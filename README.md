# NTFS 只读恢复工具

> **NTFS read-only recovery tool** — extract files from a corrupted NTFS volume
> that Windows reports as RAW. It bypasses the filesystem driver, scans the whole
> MFT table, and rebuilds the directory tree from the parent reference stored in
> each record. Works even when the root directory record itself is destroyed.
>
> Read-only by design: it never writes to the source disk.

针对「文件系统损坏、卷显示 RAW、根目录丢失、文件复制不出来」的机械盘 / 固态盘，
把里面的照片、视频、文档按原始目录结构恢复出来。

**全程只读，不对源盘做任何写操作。**

---

## 快速开始

双击 `启动.bat`（会自动申请管理员权限），浏览器自动打开界面。

需要管理员权限的原因：读取 `\\.\PhysicalDriveN` 原始设备必须提权。
如果没提权，程序会自动退回到卷句柄（`\\.\E:`）模式，功能不受影响，
但卷没有盘符时就无法读取。

### 操作流程

1. **选磁盘** — 列表里挑出故障盘（看型号和容量）
2. **选分区 → 诊断** — 检查引导扇区、MFT 前 16 条记录，判断根目录是否损坏
3. **扫描** — 顺序读取整张 MFT 表，按父目录引用重建目录树（1.2M 条记录约 4 分钟）
4. **浏览勾选** — 目录树逐层点进去，勾选要恢复的文件；顶部会列出「图片最多的文件夹」
5. **提取** — 填目标文件夹，开始复制

扫描结果会缓存到 `.cache/`，下次打开不用重扫。

---

## 它解决什么问题

常规工具从「卷 → 根目录 → 子目录 → 文件」这条链走。一旦根目录所在的
MFT 第 5 条记录损坏，链条第一环就断了，Windows 判定为 RAW，工具只能看到空卷。

但 NTFS 的每条文件记录都是**自包含**的：文件名、父目录记录号、数据所在的簇，
全都写在自己的 1024 字节里。所以本工具绕开根目录，直接：

1. 读引导扇区拿到 MFT 起始位置和簇大小
2. 解析 `$MFT` 自己的数据段（可能碎片化成上百段，还会分散在多条记录里）
3. 顺序扫完整个 MFT，从每条记录提取「父目录引用 + 文件名」
4. 反向聚合重建整棵树

## 实现要点

| 模块 | 作用 |
|---|---|
| `RawDevice` | 按 1 MB 块读原始设备，每块独立线程 + 超时，坏道跳过不卡死 |
| `parse_boot` | 解析 NTFS 引导扇区 |
| `parse_runlist` | 解析数据段列表（支持稀疏段、变长编码） |
| `parse_record` | 解析 MFT 记录：`$FILE_NAME` 取父目录和文件名，`$DATA` 取数据段 |
| `Volume` | 分区级封装：MFT 定位、记录读取、整表扫描、文件提取 |

几个容易踩的坑，代码里都处理了：

- **原始设备读必须扇区对齐**，否则 `OSError: [Errno 22]`
- **`$MFT` 自己的 runlist 可能跨记录**，需要顺着 `$ATTRIBUTE_LIST` 追到扩展记录
- **扩展记录没有 `$FILE_NAME`**，不能因为没名字就丢掉（它承载着 `$DATA` 片段）
- **同名多条记录**：旧记录可能指向已被回收的簇，按「取最大」挑正确的那条
- **坏道读取会挂起十几分钟**：线程 + 超时 + 换句柄
- **文件末尾按簇补零**：DJI 等设备的文件结尾不是 `FFD9`/`moov`，校验要往后扫

## 依赖

- Windows + Python 3.8+
- `dissect.ntfs`（仅用于解析 `$MFT` 的 runlist，其余全部自带实现）

```bash
pip install dissect.ntfs
```

没有装也能跑：会自动退回内置的 runlist 解析器，只是对极度碎片化的
`$MFT` 支持不如 dissect 稳。

## 打包成 exe

运行 `打包exe.bat`，产物在 `dist\NTFS恢复工具.exe`（约 12 MB）。

**⚠️ 本机可能跑不起来**：这台电脑开启了「智能应用控制」（Smart App Control，
`VerifiedAndReputablePolicyState = 1`），它会拦截所有未签名、无信誉的 exe，
报错是「应用程序控制策略已阻止此文件」。

三个选择：

| 方案 | 说明 |
|---|---|
| **继续用 `启动.bat`** | 推荐。Python 解释器是签名的，不受策略影响，功能完全一样 |
| 关闭智能应用控制 | 设置 → 隐私和安全性 → Windows 安全中心 → 应用和浏览器控制 → 智能应用控制。**注意：关闭后无法重新开启，除非重装系统** |
| 代码签名 | 需要购买代码签名证书（一年几百到几千），签完才能被识别为可信 |

打包本身没问题，exe 在没有 SAC 的机器上可以直接运行。

## 能力边界

**支持**：NTFS 逻辑损坏 —— 根目录丢失、分区表损坏、文件系统结构损坏、断电后变 RAW。

**不支持**：

- **物理损坏** —— 有咔哒异响、摔过、进水的盘，不要通电，直接送无尘室开盘
- **exFAT / FAT32** —— 结构完全不同，需要另外实现
- **加密卷** —— BitLocker / VeraCrypt 需要先解锁
- **数据雕刻** —— 记录已被覆盖的文件（读出内容是别的文件的数据）本工具救不了，
  只能按文件头签名在整盘上硬搜，会丢失文件名和目录结构

---

## 使用建议

1. **先诊断再动手**，确认是逻辑损坏而不是物理损坏
2. **恢复出来的数据立刻做两份备份**，别再放回原盘
3. **原盘恢复完就格式化**，文件系统受过一次损伤，不适合继续存重要数据
4. 遇到读不出来的坏块，工具会跳过并在扫描结束时报告数量，不会卡死

---

## 安全说明

- 程序对源盘**只做读取**，代码里没有任何写入源设备的调用
- 需要管理员权限只是为了打开原始设备句柄，不代表会修改系统
- 唯一的写操作是把恢复的文件写到你自己指定的目标目录
- 因为行为特征（遍历磁盘、大量读取），杀毒软件可能误报，属于正常现象

## 上传到 GitHub 前

仓库里**只放源码**，别放这些东西：

| 不要提交 | 原因 |
|---|---|
| `.cache/` | 里面是源盘完整文件名列表，属于个人隐私 |
| `dist/` | 12 MB 二进制，会把仓库撑大且无法 diff |
| `*.log` | 可能含本机路径 |
| 真实恢复出来的文件 | 隐私 |

`.gitignore` 已经配好了，直接 `git add .` 不会带进去。

### 关于 exe

**不建议把 exe 提交进仓库**，两个原因：

1. 二进制进 git 历史后就删不掉了，仓库会一直背着这 12 MB
2. 未签名的 exe 会被 SmartScreen 和杀软拦，下载的人体验很差

推荐做法：代码走仓库，exe 走 **Releases**（GitHub 允许单文件 2 GB，且不占 git 历史），
在 Release 说明里写清楚「未签名，Windows 可能提示风险，介意请用源码运行」。

### 不需要做的事

- **不需要「加固」或加壳**：加壳只会让杀软误报更严重
- **不需要代码签名**：除非要正式分发，个人项目跳过；想签的话一年几百到几千
- 需要的话只加一个 `LICENSE`（仓库里已附 MIT 模板，把 `<你的名字>` 改掉）
